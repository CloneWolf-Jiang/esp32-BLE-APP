项目开发任务：ESPHome 三键智能开关蓝牙配网 Android APP

请以资深 Android 工程师、嵌入式通信工程师、UI/UX 设计师和测试工程师组成的成熟商业软件团队的标准，开发一款能够真实运行的 ESPHome 智能开关蓝牙配网 APP。

本项目不是静态 UI 演示，不接受仅实现页面跳转、模拟 BLE 设备或伪造配网成功状态的交付。

在开始编写代码之前，必须先核实 ESPHome 官方 Improv over BLE 协议、当前固件能力、Android BLE 兼容性和 Wi-Fi 扫描限制。

---

一、项目背景

硬件为基于 ESP32-C3 的三键智能开关，固件使用 ESPHome。

设备通过 ESPHome 原生 Improv over BLE 功能完成首次 Wi-Fi 配网。由于使用手机浏览器进行配网不够方便，我希望开发独立 Android APP，为用户提供完整、直观、可靠的蓝牙配网体验。

设备具有以下明确的交互约定：

- 面板共有 3 个实体按键。
- 使用面板最左侧的 1 号按键作为蓝牙配网物理授权按钮。
- 用户需要持续长按 1 号按键 5 秒。
- 长按成功后，设备进入蓝牙配网授权状态，有效期为 1 分钟。
- 设备侧没有可视化反馈，不能依靠 LED、屏幕、蜂鸣器等反馈判断授权成功。
- APP 必须主动引导用户操作，并通过真实 BLE 协议交互判断后续流程是否可继续。
- 不能为了实现配网而误触发继电器控制或改变正常负载开关状态。

以上按键行为是产品需求。若现有 ESPHome 配置尚未实现该行为，应明确指出需要修改固件，不能假定仅编写 APP 就能实现物理授权。

二、技术目标与 Android 兼容性

2.1 平台

- 开发语言：Kotlin。
- 最低支持 Android 5.0，minSdkVersion = 21。
- 使用适合 BLE、异步状态管理和现代 UI 的稳定技术。
- 优先评估 Jetpack Compose；必须验证所选 Compose 及相关依赖是否支持 API 21。如不满足，使用经过验证的 Android Views 与兼容的 Material 组件。
- 使用 AndroidX、Gradle Kotlin DSL 和 Gradle Wrapper。
- targetSdkVersion 应选择开发时适合正式发布的稳定 API 级别，兼顾华为应用市场的现行要求及 Android 权限规则。
- 不得通过降低 targetSdk 来规避新系统的权限限制。
- 所有依赖必须真实存在，且与最低系统版本兼容。

2.2 UI 设计

采用现代、简洁、专业的智能家居产品设计风格。

要求：

- 统一设计系统，包括颜色、字体、间距、圆角、图标和组件状态。
- 支持浅色和深色主题。
- 支持不同尺寸屏幕、系统字体缩放和系统导航栏。
- 中文作为首发语言，并为国际化预留资源结构。
- 具备完整的加载、空状态、错误、权限拒绝、连接中断和成功页面。
- 禁止无功能按钮、虚假统计信息和仅用于演示的交互。
- 优先使用清晰的页面层级和适度留白，不采用过度装饰的模板风格。

三、ESPHome 原生 Improv over BLE 协议

这是整个项目最重要的技术要求。

首先阅读并核实：

1. ESPHome 官方文档：
   https://esphome.io/components/improv_ble/
2. Improv Wi-Fi BLE 协议规范：
   https://www.improv-wifi.com/ble/
3. ESPHome 官方源代码：
   https://github.com/esphome/esphome

注意：ESPHome 从 2026.10.0 开始将 "esp32_improv" 更名为 "improv_ble"，旧配置名是兼容别名。开发时应以目标固件的实际 ESPHome 版本为准。

3.1 协议核实

必须确认并记录：

- Improv BLE 服务 UUID。
- 所需 GATT 特征 UUID、属性和数据格式。
- 服务发现、状态读取、RPC 写入和响应通知的正确顺序。
- 协议版本及分包规则。
- 设备授权状态和配网状态的识别方式。
- Wi-Fi 扫描命令、Capabilities 特征和网络列表返回格式。
- 设备信息查询、设备名称查询等可选功能的支持条件。
- 连接超时、未授权、凭据无效、无法联网和服务停止等错误的处理方式。

不得自行猜测 UUID、RPC 编号、响应格式或错误码。应从官方规范和对应版本源码中核实后实现。

3.2 设备发现与识别

APP 必须使用真实 BLE 扫描结果。

设备识别应结合 Improv 服务标识和协议特征，不能只依据设备名称中是否包含 ESPHome。

必须处理：

- 设备名称为空。
- 重复扫描结果。
- 同名设备。
- 设备离开扫描范围。
- 扫描超时。
- 用户主动停止扫描。
- 蓝牙关闭或权限被拒绝。

3.3 物理授权状态

必须区分以下状态：

- 尚未扫描。
- 正在扫描。
- 发现目标设备。
- 正在连接。
- 已连接但尚未授权。
- 等待物理授权。
- 已获得协议授权。
- 正在提交配网信息。
- 正在连接 Wi-Fi。
- 配网完成。
- 配网失败或超时。

APP 不得将 BLE 连接成功等同于物理授权成功。

当设备需要授权但尚未授权时，应提示用户执行长按操作。只有协议实际返回的授权状态能够证明授权完成时，APP 才可以进入凭据提交阶段。

如果协议或当前固件无法向 APP 提供足够的授权状态信息，应明确说明限制，并设计可行的重试和超时机制，不得虚构授权状态。

四、长按 1 号按键的配网引导

这是强制功能。

4.1 操作要求

配网流程开始后，先显示独立的操作指引页面：

- 标题：让智能开关进入配网模式。
- 显示三键开关的示意图。
- 明确标出最左侧的 1 号按键。
- 明确提示持续长按 5 秒。
- 说明设备没有灯光或其他可视化反馈。
- 告知用户松开按键后，授权窗口有效期为 1 分钟。
- 提供“开始扫描”和“重新查看指引”操作。

不得将其他两个按键标记为配网授权按钮。

4.2 授权窗口

将授权有效期作为可配置常量，默认值为 60 秒。

必须考虑：

- 用户按下按键前，APP 已经打开。
- 用户在操作指引页完成长按后再开始扫描。
- 用户先扫描并连接，随后才进行物理授权。
- 用户操作过慢，导致授权窗口到期。
- BLE 连接建立时授权已失效。
- 用户在配网过程中离开页面。
- 设备在授权窗口内被其他客户端连接。

应允许用户重新进行授权操作，并提供明确的重新尝试入口。

APP 不得声称自己能直接检测按键长按动作，因为物理按键事件发生在 ESP32 固件内部，除非设备实际通过协议提供相关状态。

4.3 ESPHome 固件配套要求

请检查现有 ESPHome 配置是否已经满足以下条件：

- "improv_ble" 使用与 1 号物理按键相对应的授权传感器。
- 按键必须持续按下 5 秒才能产生授权事件。
- 短按、抖动或其他按键操作不能意外授权。
- 授权有效期为 1 分钟。
- 授权失效后不能继续提交 Wi-Fi 凭据。
- 配网授权逻辑不能误触发继电器输出。
- 对按键事件和配网状态进行必要的日志记录，但不得记录敏感凭据。

如果当前固件没有实现以上功能，请单独输出 ESPHome 配置修改建议，并清楚区分 APP 代码和固件代码的职责。不要擅自覆盖现有配置。

五、Wi-Fi 网络搜索策略

这是本项目的第二项核心技术任务。

必须优先分析 ESPHome 原生 Improv BLE 协议能否获取设备端扫描的 Wi-Fi 网络列表。

采用以下优先级：

1. 设备端扫描：若设备固件支持 Improv BLE 的 Scan WiFi 命令，且实际返回的网络列表可以正确解析，则优先使用设备端结果。
2. 手机端扫描：若设备端不支持该功能、Capabilities 未声明支持，或者命令不可用，则尝试通过 Android 系统 API 获取附近 Wi-Fi 网络。
3. 手动输入：若手机扫描不可用、权限不足、系统限制导致扫描结果不完整，或者用户需要连接隐藏网络，则必须允许手动输入 SSID。

5.1 设备端扫描

必须先读取设备的 Capabilities 特征，判断是否支持 Wi-Fi 扫描。

只有设备确实支持时，才能发送相应 RPC 命令。

要求：

- 解析真实返回的 SSID。
- 处理空列表、重复 SSID、响应超时和扫描失败。
- 不得根据设备名称或其他不相关字段推测 Wi-Fi 列表。
- 不得将协议不支持的功能伪装成已支持。
- 不得将空列表直接解释为附近没有 Wi-Fi 网络。

5.2 手机端扫描

使用适合 Android 版本的系统 Wi-Fi 扫描 API。

必须考虑：

- Android 5.0 至 Android 8.1 的旧权限和扫描行为。
- Android 9 及以上版本对 Wi-Fi 扫描频率和权限的限制。
- Android 10 及以上的定位相关权限和系统定位状态要求。
- Android 13 及以上的附近 Wi-Fi 设备相关权限规则，判断其与具体 API 的实际关系。
- 系统扫描频率限制、扫描缓存及厂商实现差异。
- 用户拒绝权限、定位服务关闭、扫描失败和扫描结果为空的情况。

不得假定调用一次扫描 API 就一定能够得到最新结果。

必须显示真实扫描状态，并在需要时提示用户授权或手动输入 SSID。

5.3 Wi-Fi 列表与输入页面

页面应包含：

- SSID 搜索框。
- 真实扫描结果列表。
- 可用的网络信息；只有真实数据支持时才能显示信号强度等字段。
- 重新扫描按钮。
- 手动输入 SSID 入口。
- 隐藏网络支持。
- 清晰的空状态和错误提示。

对于设备端与手机端的扫描结果，应在内部记录数据来源，以便排查兼容性问题。

不能假定手机能够连接的网络一定可被 ESP32-C3 连接。实际联网能力由设备的 Wi-Fi 硬件、频段、网络安全模式及路由器配置决定。

六、Wi-Fi 凭据提交

要求：

- 显示最终选择的 SSID。
- 默认掩码显示密码。
- 提供显示/隐藏密码操作。
- 支持用户确认后提交。
- 通过已核实的 Improv BLE 协议发送 SSID 和密码。
- 正确处理协议响应和错误码。
- 不得把提交请求成功误认为 Wi-Fi 已连接成功。
- 使用设备真实返回的配网状态判断后续结果。

敏感信息处理：

- 不在普通日志中打印明文密码。
- 不将密码写入 SharedPreferences、数据库或普通文件。
- 不上传密码至第三方服务。
- 断开连接或流程结束后，尽可能释放不再需要的敏感数据。
- 不得为了自动重试而擅自长期保存用户密码。

七、配网状态机与错误处理

必须设计明确的状态机，并将 BLE 层、协议层、业务状态和 UI 状态分离。

至少实现以下流程：

启动
→ 操作指引
→ 蓝牙和权限检查
→ BLE 扫描
→ 选择设备
→ 建立连接
→ 发现 GATT 服务
→ 读取协议能力
→ 判断授权状态
→ 等待物理授权（如需要）
→ 获取 Wi-Fi 列表
→ 选择或输入 SSID
→ 输入密码
→ 提交凭据
→ 等待设备联网
→ 成功或失败。

错误分类至少包括：

- 蓝牙未开启。
- 权限拒绝。
- 未发现设备。
- 连接失败。
- GATT 服务不匹配。
- 协议初始化失败。
- 物理授权尚未完成。
- 授权窗口已超时。
- Wi-Fi 扫描不受支持。
- Wi-Fi 扫描失败。
- 用户输入无效。
- 凭据提交失败。
- 设备无法连接 Wi-Fi。
- 设备响应超时。
- 配网过程中断连。
- 设备已离线或配网服务已停止。

每种错误都应有用户能理解的提示和合理的恢复入口。

不能用单一的“配网失败”提示掩盖所有错误，也不能通过固定延迟后显示成功来模拟真实配网。

八、架构与工程规范

采用清晰、适度的分层结构：

- UI 与导航层。
- ViewModel 或等效状态管理层。
- 配网业务与状态机层。
- Improv BLE 协议层。
- BLE GATT 通信层。
- Android 权限与 Wi-Fi 扫描适配层。
- 测试与日志层。

要求：

1. BLE 操作采用异步执行。
2. 必要时串行化 GATT 操作，避免并发读写导致状态错乱。
3. 正确管理连接、通知订阅和资源释放。
4. 处理页面重建、生命周期变化和连接中断。
5. 避免重复扫描、重复连接、内存泄漏及回调竞态。
6. 使用明确的数据模型和类型安全的状态定义。
7. 协议解析逻辑必须能够独立测试。
8. 禁止在生产代码中使用模拟设备或虚构配网结果。
9. 不引入与核心功能无关的广告、分析、账号或云端服务。
10. 所有依赖、类名和 API 必须真实有效。

九、测试与验收

必须提供自动化测试和真实设备验证方案。

9.1 协议测试

- 服务 UUID 与特征 UUID 验证。
- Capabilities 解析。
- RPC 请求和响应解析。
- Scan WiFi 支持与不支持两种情况。
- 授权前和授权后的流程差异。
- 配网状态和错误码解析。
- 超时、断连、通知丢失和异常数据处理。

9.2 功能测试

- 未长按 1 号按键时，不得假定已授权。
- 长按 5 秒后，在授权有效期内可以继续配网。
- 超过 1 分钟后，能够识别授权过期并引导用户重新操作。
- 不得因为长按配网按键而误触发继电器。
- 设备端支持扫描时，优先使用真实设备端列表。
- 设备端不支持扫描时，自动转向手机扫描。
- 手机扫描失败时，仍可手动输入 SSID。
- 错误密码、设备断连及设备无法联网时，能够正确显示失败结果。
- 成功结果必须来自真实协议状态，而非模拟逻辑。

9.3 Android 兼容性测试

重点验证：

- Android 5.0 / API 21。
- Android 6 至 Android 11 的旧权限机制。
- Android 12 及以上的蓝牙权限。
- Android 13 及以上的 Wi-Fi 扫描相关权限和系统限制。
- 当前主流 Android 版本。
- 不同厂商的蓝牙与 Wi-Fi 实现差异。

如果无法取得全部测试设备，必须明确列出哪些版本已经实测、哪些仅通过自动化测试、哪些尚未验证。

十一、执行顺序

第一阶段：官方文档与源码核实，输出技术可行性分析。

第二阶段：确认协议能力、授权机制和 Wi-Fi 扫描降级方案，输出架构与状态机。

第三阶段：先实现真实 BLE 扫描、连接和 Improv 协议，再开发完整 UI。

第四阶段：完成端到端配网、异常恢复和兼容性测试。

第五阶段：完成项目构建、交付 APK 和源码，列出真实测试结果。

请立即从第一阶段开始，不要跳过协议核实，也不要先生成大量未经验证的代码。

如发现现有 ESPHome 固件不能实现某项需求，应说明需要修改的固件配置及其原因，并在不破坏现有智能开关功能的前提下提出方案。
